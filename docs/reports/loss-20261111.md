## 一句话结论

**失败的轨迹里，将近一半（48%）是模型打转或失控**：重复同一个调用被插件强制收尾（24%），用满 12 步被强制收尾（12%），输出写到超长被截断或格式坏掉（12%）。真正“老老实实做完但答错”的只占约三成。
打转集中在写代码的几块（web-code、code-fix、terminal），这三块加起来占了全部失分的 42%。编辑文件失败是打转的重要诱因：**20% 的失败轨迹里至少有一次编辑报错**。

## 2. 失败的直接原因

对每次失败的轨迹，按下面的顺序取第一个命中的原因：超时 → 输出截断或无法解析 → 重复调用被强制收尾 → 用满 12 步被强制收尾 → 编辑失败没补救 → 一个文件都没改 → 工具选择问题 → 改了文件但测试仍不过 → 判分器给的原因（答错、文件结果错）。这是启发式归类，排在前面的原因优先。

| 直接原因 | 新：占失败次数 | 新：占全部次数 | 旧：占全部次数 |
|---|--:|--:|--:|
| **重复调用被强制收尾** | 23.8% | 10.0% | 10.8% |
| 答错（内容不对） | 22.5% | 9.4% | 12.7% |
| **用满 12 步被强制收尾** | 12.2% | 5.1% | 6.2% |
| **输出超长被截断，或格式坏掉要重问** | 11.8% | 5.0% | 4.9% |
| 文件结果错（改了但内容不对） | 8.2% | 3.5% | 3.6% |
| 一个文件都没改 | 5.8% | 2.5% | 1.9% |
| 改了文件，测试仍不过 | 5.7% | 2.4% | — |
| 没调题目要求的工具 | 3.5% | 1.5% | 1.3% |
| 编辑失败、到最后也没改成 | 3.3% | 1.4% | — |
| 不该调工具却调了 | 2.3% | 1.0% | 1.0% |
| 搜索题没搜就答 | 2.0% | 0.9% | 1.3% |

和旧模型比，新模型主要减少了“答错”（12.7% → 9.4%），打转类基本没变。也就是说，**这轮补的数据改善了做题质量，没有改善打转。**

### 2.1 打转的三种形态

插件 trace（插件记录每一步决策的日志）里的数据，按 trial 计：

| 插件干预 | 发生在多少次跑分里 | 这些跑分的通过率 | 没发生时的通过率 |
|---|--:|--:|--:|
| 第一次重复同一调用，插件提醒并给一次机会 | 1003（24.6%） | 25% | 69% |
| 再次重复，或同一个失败调用原样重试，插件强制收尾 | 546（13.4%） | 11% | 65% |
| 一轮用满 12 次工具调用，强制收尾 | 493（12.1%） | 14% | 64% |
| 模型输出写到长度上限被截断 | 197（4.8%） | 11% | 60% |
| 模型输出无法解析，插件要求重答 | 229（5.6%） | 12% | 61% |

- **被判重复的是哪个工具**（两次跑分合计的强制收尾）：bash 155、edit 133、read 124、web_fetch 64、write 53、grep 45。edit 的 133 次是同一个失败的编辑原样再发一次，也就是编辑失败后不会换写法。
- **输出截断**：抽查 rc.1 那次的 128 次截断，72% 是思考已经结束，正文却没调工具，一直往下写。68% 结尾在重复前面的内容，典型的是凭空编造一段测试输出，或者一个个枚举情况停不下来。这是 RNN 常见的复读退化。
- **12 步上限**：插件默认每轮用户对话最多 12 次工具调用（`maxSteps: 12`），到了就收走工具、让模型直接作答。用满的跑分通过率只有 14%，多半本来就在打转。但其中有没有“还在推进、只是步数不够”的，要做实验才知道，比如把上限调到 20 跑一次代码类题。

### 2.2 多轮题明显更难

| 能力块 | 单轮题通过率 | 多轮题通过率 |
|---|--:|--:|
| code-fix | 83.9 | 34.5 |
| read-code | 76.8 | 16.4 |
| read-local | 77.6 | 48.5 |
| web-code | 36.9 | 16.9 |
| terminal | 16.7 | 4.2 |
| stat | 55.4 | 43.4 |
| search | 87.7 | 73.3 |
| web-local | 57.6 | 76.0 |

（“轮”指用户发了几次消息，不是工具步数。）

多轮题和题目难度是混在一起的：比如 code-fix 的多轮题多是多模块项目，所以这里不能直接算成“多轮本身造成的损失”。几个具体点：

- **read-code 多轮的 97 次失败里，44 次是“第 3 轮没调 read”**，全部来自 `own-rc-*` 这一组题。模型在第 3 轮直接根据前面读过的内容作答，判分器要求这一轮必须调 read。这里可能有一部分是判分过严，要人工看一下。
- **code-fix 和 web-code 的多轮失败**以输出截断、重复调用、用满 12 步为主。后面几轮上下文变长，打转更多。

## 3. 工具层面：哪些调用容易出错

新模型合并两次跑分，共 4076 次 trial：

| 工具 | 调用次数 | 报错率 | 主要错误 | 有这种报错的跑分通过率 / 没有的 |
|---|--:|--:|---|---|
| **edit** | 2353 | **27.7%** | 原文找不到 506，新旧内容相同 132，原文不唯一 8 | **12.8% / 74.6%** |
| web_search | 893 | 17.1% | 题目没开搜索却去搜 143（题面已经给了网址） | 30.6% / 85.6% |
| web_fetch | 1202 | 11.7% | 141 次全是 HTTP 404（网址是编的或拼错的） | 52.9% / 51.6% |
| grep | 784 | 8.4% | 搜索失败 64（路径不存在） | 26.3% / 51.0% |
| read | 8748 | 5.7% | 文件不存在 356（路径是编的），读的是目录 144 | 48.4% / 54.8% |
| write | 1355 | 1.3% | 多填了沙箱参数 `justification` 被拒 11 | 35.7% / 45.2% |
| bash | 7370 | — | DSH 不把非零退出码当错误；单看退出码：2545 次非零（分布在 1001 次跑分里），其中命令不存在（127）44 次 | — |

- **编辑是出错率最高的工具**，影响也最大：335 次失败轨迹（失败总数的 19.6%）里出现过编辑报错。“原文找不到”的细分见下一节。
- “新旧内容相同”132 次：模型想改，结果写的新内容和原文一模一样，通常是改了个寂寞，或者忘了改。
- 题面给了网址、环境没开搜索时，模型仍会调 web_search（143 次），说明它没读懂“打开题面给的网址”这个提示。
- “有报错时通过率更低”只是相关，不是因果：难题本身报错也多。但编辑这一项差距太大（13% vs 75%），基本可以认定是编辑失败把轨迹带进了打转。

## 4. 编辑失败细看（同日已做的实验）

- **“原文找不到”约 97% 发生在已经读过文件之后**，即模型抄原文抄错了，RNN 逐字复制长内容本来就弱。
- **改提示词没用**：在 416 道编辑题上试了改工具描述、加系统提示规则、两者都改，编辑失败率都在 27.5%–28.5%，和基线 28.1% 一样（`experiments/edit-prompt/`）。
- **hashline（读文件时每行带标记，编辑时只写标记）零样本不会用**：基模 18.3 → 1.9 分，只有 3% 的编辑调用写了新参数（插件分支 `hashline-edit`）。
- **容错匹配离线重放**：今天两次跑分里 1094 次能可靠还原的“原文找不到”中，Aider 式的“整段缩进统一偏移，对齐后再改”能安全救回 148 次（13.5%）。更宽松的模糊匹配虽然能“救”得更多，但会把缩进写坏或改错地方，Aider 和 opencode 都已经撤掉了这类匹配。**剩下约 72% 是内容本身抄错了**，只能靠换编辑方式加训练来解决。

## 5. 待解决清单（先列出，集中处理）

按“谁来改”分组，括号里是大约涉及的失败比例（占全部失败次数，可能有重叠）：

**插件（不改模型看到的内容，可以直接改、直接测）**
1. 编辑兜底：精确匹配不到时，尝试 Aider 式缩进对齐（约救回 14% 的“原文找不到”）。
2. 12 步上限：用代码类题做实验，比如上限 12 对 20，看用满步数的那 12% 里有多少是步数不够、多少是本来就在打转。
3. 写入、编辑时多填的 `justification` 等沙箱参数，在插件里直接去掉（write 报错的主要来源）。

**插件 + 训练数据（会改模型看到的内容，要按铁律三边一起动）**
4. 编辑方式：行号或 hashline 二选一，重采 435 道含编辑的题（编辑出错率 27.7%，涉及 19.6% 的失败）。
5. 编辑失败时，在报错里附上文件中最接近的几行（opencode 的做法），让模型重试时从最近的上下文里抄。

**训练数据**
6. 打转（48%）：补“失败后换办法”的轨迹，比如编辑失败后重读再改、命令报错后换命令、测试不过时先看报错再改，而不是原样重发。还要检查训练包里有没有教模型复读的样本（按轨迹质量闸门扫一遍）。
7. 输出截断：思考结束后正文写长、编造测试输出、复读，补短而准的收尾样本，必要时降低截断前的最大输出长度。
8. 题面给了网址时直接 fetch，不要去 search（143 次）；路径不要靠猜，先 glob 或 ls（read 文件不存在 356 次、读目录 144 次）。
9. terminal 这一块：唯一退步的块，4 次全错的有 44/60 道，训练包里没有这类题（`终端操作-Shell` mix 为 0 行）。

**判分器**
10. `own-rc-*` 多轮题第 3 轮“必须调 read”的要求，人工看一下是否过严（read-code 多轮失败的 44 次）。
