# 新版 Web 搜索 API 开关前后的搜索质量对比（2026-11-09）

## 一句话结论

打开开关后，**搜到的网页基本还是同一批**（8 条来源里平均有 6.5 条重合）。差别在于模型能看到什么：

- **关着（旧版）**：模型只拿到"标题 + 链接"，**一条摘要都没有**。36 道事实题里，答案出现在模型可见文本中的只有 15 道（42%），而且全是因为答案碰巧写在标题或链接里。
- **开着（新版）**：每条来源都带摘要，36 道里 35 道的答案就写在结果里（97%）。剩下 1 道，结果里给的是旧文档的数值（140 TB），算上也是 36/36。
- 代价是结果变长：每次搜索平均 **4258 字符**，旧版 1273 字符，约 3.3 倍，最长 7816 字符。
- 新版还快一个数量级：中位耗时 **0.35 秒**，旧版 3.7 秒；也不再额外花 `deepseek-v4-flash` 的 token。

## 测法

- 脚本：`scripts/search-compare.mjs`；题目：`scripts/search-compare-cases.json`；原始结果在 `runs/search-compare-2026-11-09/`（`results.jsonl` 里有模型看到的完整文本，未入库）。
- 41 个查询：36 道有标准答案的事实题（端口号、版本代号、arXiv 编号、发布日期、常识数值，中英各半），外加 5 道时效题（新闻、股价、天气、最新版本），时效题只统计带日期的来源数。
- 三组，每组每题调用一次，请求格式和 DSH 0.2.2-rc.1 的代码一致：
  - **legacy**：`web-search-deepseek`，调 Messages API 让 `deepseek-v4-flash` 用原生 `web_search` 工具（最多搜 5 次）；
  - **api**：`web-deepseek-api` 的 Search API，`count=8`，带 `ori_question`（用户原问题，DSH 默认就带）；
  - **api_noq**：同上，但不带 `ori_question`。
- 结果按 `tool-web` 的 `formatSearchOutput` 拼成模型实际看到的文本：最多 8 条来源，摘要压成一行、截到 800 字符。
- **"命中"的意思是答案字符串出现在这段文本里**，即模型不用再抓网页就能答。它不等于模型最终答对。每题只发一个查询，RWKV 实际常一次发 2–4 个，但 DSH 合并后同样最多保留 8 条。

## 结果

| 指标 | legacy（关） | api（开） | api_noq |
|---|---|---|---|
| 报错 | 0/41 | 0/41 | 0/41 |
| 事实题答案出现在结果文本里 | **15/36（41.7%）** | **35/36（97.2%）** | 35/36 |
| 只看标题和链接就能命中 | 41.7% | 44.4% | 44.4% |
| 每次来源数 | 8 | 8 | 8 |
| 带摘要或片段的来源 | **0** | 8 | 8 |
| 带发布日期的来源 | 0 | 5.5 | 5.4 |
| 时效题里日期为 2026 年的来源 | 0（没有日期） | 4.4 | 4.0 |
| 不同域名数 | 6.2 | 6.2 | 6.1 |
| 结果文本长度（平均/中位） | 1273 / 1254 字符 | 4258 / 4262 字符 | 4251 / 4206 字符 |
| 中位耗时 | 3.7 秒 | 0.35 秒 | 0.33 秒 |
| 额外模型开销 | 每次约 3400 输入 + 450 输出 token（flash） | 无（Search API 单独计费） | 无 |

几点观察：

1. **旧版不是搜得差，而是把内容丢了。** 两边返回的链接平均重合 6.5/8，底层是同一个搜索源。旧版 DSH 只从 flash 回复的 `citations` 里取片段，这次 41 次调用一次都没取到；flash 自己写的那段文字回答（平均约 450 输出 token）DSH 也不交给模型。所以旧版下，模型想知道任何内容都得再调 `web_fetch`。
2. **`ori_question` 几乎没影响。** 带和不带用户原问题，41 题里有 39 题返回的来源列表完全一样，另外 2 道时效题略有不同。新版质量好，来自摘要，不是来自它理解了用户意图。
3. **新版只是更长，内容并不脏。** 摘要多是网页里和查询相关的几段原文，中间用 `...` 连接（例如 Redis 那题，8 条里有 7 条直接写了 6379）。但一次搜索就是 4–8 千字符。08:49 那个 RWKV 会话里，一次搜索后提示词从 6.3k 涨到 14.7k 字符，就是这个原因。
4. **训练数据里没有这种形态。** 管线的 `fixture-web` 只给标题、链接和短片段，`real-web` 的搜索直接报"不可用"，评测的 `web-replay` 也一样。模型没见过"每条都带一段长摘要、摘要里还夹着别的链接"的结果。

## 对 RWKV 的含义

- 开着新版时，大多数事实题**搜一次就能答**，不用再抓网页。这对 RWKV 有利：工具步数更少，也少踩 `web_fetch` 的坑。
- 但模型需要学会两件事：①摘要里已经有答案时直接回答并引用链接；②摘要里出现别的链接时，一次只抓一个。现在这两样训练数据里都没有。
- 要让训练和评测跟上，fixture / replay 要支持 `summary` 字段，并按新版的长度和格式造题。存档时可以直接用 Search API 的原始返回，评测以前抓存档用的也是同一个接口。
