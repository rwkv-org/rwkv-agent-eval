# adapter g1l-nora-r16-lr2e-5-e2 评测归因与补数据方向（2026-11-07）

被测：基模 `rwkv7-g1l-7.2b-20261031-ctx34304` 对比在 mix-20261106 上训的 NoRA adapter `g1l-nora-r16-lr2e-5-e2`。
题库 1019 题（第一版选题 435 + 留出题补题 135 + 第二轮自造新题 449），每题每个模型 2 次，统计按“先求每题平均，再在题目层面算误差”，差值是同题配对差 ±95%。
看板：`runs/server/dashboard-final.html`；全部表格：`runs/server/attribution-final.{md,json}`（`runner/attribution.py` 生成）。

## 结论（先看这里）

1. **总分 基模 30.9% → adapter 52.8%，+21.9 ±3.2 个点，非常显著，12 个能力块全部是涨的。** 涨幅最大的就是训练数据最多的地方：真实网页两个领域（1781 行，占 Agent 数据 38%）把“网页+本地”从 3.5% 拉到 59.7%；代码修复从 15.3% 到 51.6%。
2. **涨分的主要机制是“学会了按题面去调对的工具”，不是更会推理。** 网页题打开网页的比例从约 35% 到约 99%；代码修复不调工具的比例从 19% 到 0%，工具报错率从 22% 降到 8%，改测试文件的次数从 39 降到 8。剩下的失败绝大部分是“做了，但做错了”（测试没过、答案错），这一类基本没有减少。
3. **数据量和涨幅只有中等相关**（26 个领域的 Spearman ρ ≈ 0.40）。数据少的领域也普遍涨了，说明工具使用习惯能跨领域迁移；但“统计计算”“查找阅读-日志”“改文件写产物-文档配置”这几个领域几乎没涨，问题不在数据量，而在于下面几种失败模式。
4. **新出现的三个坏习惯**是下一轮数据最该补的地方：
   - **改完文件后重复读同一个文件做核对**，撞上插件的重复调用保护，这一轮就以“没能整理成答案”收尾。adapter 的 245 次收尾里有 104 次属于这一种。训练数据里有 290 条“改完再读”的目标步，却**没有一条**教过被拒之后该怎么答（0 条）。
   - **在 `<think>` 里逐行抄日志来手工计数**，一步就生成 7000～9000 字符。统计块的 19 次超时基本都是这个原因。训练数据里统计类样本的思考中位数只有约 240 字符，而且有 62 条是用 bash 命令计数的，所以这是基模的旧习惯，数据没能压住。
   - **能答就不搜**：搜索题里，adapter 失败的 69% 是“没调 web_search 直接答”，包括题面明确写了“请上网查询”的题（own-se-023）。
5. **掉分集中在“直接回答-做不到”（-14.7 个点）**：adapter 拒答本身是对的，但拒答前要先用 bash/glob 探一下环境，被“本轮不应调用工具”的判据判错（own-dr-042、own-dr-043、own-dr-044、nt-33174）。这一类训练数据只有 25 行。
6. **终端操作（没有训练数据）从 0 到 10.8%**，涨得很少。失败几乎都是“汇总的数值或行顺序不对”，以及用满步数没给答案。参考答案在评测同款 Debian 容器里全部能通过，所以题本身没问题。

## 4. 题库与判分的可信度

- **新题质量**：449 道新题由 Codex 造、另一个 Codex 逐题审（改了大部分题的判据，删 8 题，剔除 3 道常识搜索题）。参考答案在评测同款 Debian 容器里 449/449 通过。两边都 0 分的新题 171 道（共 449 道新题），集中在终端（50/60）和网页+代码（53/88）。抽查失败轨迹都是模型真做错，不是题坏；但这些题对现在的 7B 区分度为零，下一版题库可以把其中一部分换成更简单的同类题。
- **判分器修复**：审旧题时发现 `required_tools` 里 DSH 的新工具名（read/grep/glob/bash）不能互相替代（旧工具名可以），已修（`bank/judge.py`），旧结果用 `runner/rescore.py` 按同样规则重判。影响：基模 4 次 trial 由错改对，adapter 0 次。
- **审题报告指出的其它判分问题**（`build/codex2/old-*.review.md`）：
  - R2：只读题里，bash 新建文件不会被发现（判据偏宽）。两边同样受益，不影响差值。
  - R3：数字匹配。全角数字会被判错，负号不会被识别；另外千分位会被判错：adapter 回答“50,000”，判据要“50000”（doc-31379）。全部 trial 里只找到这 1 题、2 次。
  - R4：名称/路径只要局部命中就算对（偏宽），两边同样受益。
  综合看，这些问题对总分的影响都在 1 个点以内，不改变结论。
- **超时口径**：adapter 推理比基模慢约 4.5 倍，所以两边都用 5 倍时限（单轮 25 分钟），第一版里 1 倍时限下超时的 trial 都用 5 倍时限补跑过。环境报错（推理服务断开连接）全部重跑成功。

## 5. 下一轮补数据优先级

| 优先级 | 领域 / 形态 | 大致条数 | 要点 | 预期影响 |
|---|---|---|---|---|
| P0 | **改完文件后的收尾**（改文件写产物各领域、代码任务、网页+代码） | 300～400 行 | 改完直接用 edit/write 的结果作答；确实要核对时，用和之前不同的调用（read 带 offset/limit，或 grep 关键行）。另外要专门做“被重复调用保护拒掉之后 → 直接根据已有结果作答”的目标步（现在是 0 条） | 收尾失败约占 adapter 失败的 2 成，主要在改文件、网页+代码、代码修复；预计这些块能涨 5～10 个点 |
| P0 | **统计计数用工具，不在思考里抄数据**（统计计算-日志/表格/跨类混合、查找阅读-日志） | 200～300 行 | 计数和过滤用 bash（grep -c、awk、sort \| uniq -c、python3 -c）；思考控制在几百字以内；行数多的日志只看命令输出 | 消除统计块的超时（19 次），统计块和日志类预计涨 10 个点以上 |
| P1 | **搜索题“题面要求搜就必须搜”**（网络查询、网络加本地） | 150～200 行 | 用真实搜索结果（DeepSeek 搜索接口存档），包括模型自认为知道答案的常识题；搭配一部分“答案就在本地文件里、不该搜”的对照样本 | 搜索块失败的 69% 来自这一类，预计涨 5～8 个点 |
| P1 | **直接回答-做不到：不探环境直接拒绝** | 80～120 行 | 外部账号、硬件、物理世界的请求：零工具调用，直接说明做不到和替代办法；搭配少量“确实需要先查本地文件”的对照样本 | 修掉做不到类的 15 个点掉分 |
| P1 | **网页+代码：读完文档后把代码改对** | 200 行 | 文档规则 → 最小修改 → 跑测试 → 根据失败输出再改一次的完整闭环；不改测试 | 网页+代码现在只有 25～29%，空间最大 |
| P2 | **终端操作（目前没有训练数据）** | 150～200 行 | 用 bash 管道/python3 做批量汇总、整理目录、写小脚本；结果写文件后用一次 bash 抽查（不是重复 read） | 终端块从 11% 起步，预计涨 10 个点以上 |
| P2 | **多轮追问时按需重新查看** | 100 行 | 追问涉及前一轮没读过的内容时，再调查看工具；只复述前一轮结果时可以不调 | 查找阅读-代码有 17 次失败属于这一类 |

另外两条不是数据问题，建议在 harness 侧处理：
- 插件的重复调用保护（`dsh-rwkv-plugin/src/core/agent.ts` 的 `gateToolCall`）在文件被 edit/write 改过之后不会重置，所以“改完读回”一律被当成重复调用。建议改成对被改过的路径重新允许 read（只有在评测和训练环境一起改时才能保持一致）。
- 带 adapter 推理慢约 4.5 倍，跑分要用 5 倍时限，整轮评测要 4～5 小时。如果推理服务能把 adapter 合并进权重，或者优化 adapter 的推理路径，评测会快很多。
