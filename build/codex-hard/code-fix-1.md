- 本批25题均逐题核对 adapter 两次的 steps、judge 与 final，并用基模作对照；主因按阻断完成任务的具体机制选择，未把 tests-failed、超时或模板话直接当作统一归因。
- 主因最多的是代码逻辑错误（code-logic，14题）：CSV 丢换行、Unicode 字节与码点混淆、False/0/null 与缺失混淆、原文偏移失效，以及复合键换分隔符仍碰撞。
- 优先补“真实输入追踪→写出局部不变量→最小修改→读取首个失败断言→修正→全套通过”的轨迹，边界用例必须实际执行，避免只在思考或最终解释中声称覆盖。
- 第二类是编辑与定位失败（cmd-error 5题、code-locate 1题）：虚构 old_string、把函数定义改成另一种写法再匹配、改错模块，以及破坏 CommonJS/ESM 导出。
- 对应补“按 imports 找定义→原样截取匹配片段→edit 失败后重读并缩小替换→核对落盘内容→先修加载错误再跑测试”的样本，并保持测试文件和只读轮边界。
- 第三类是主体修复后未完成多轮交付（066、099、102、113）：分别在具体数组计数、JSON 报告结构/路径、明确布尔答案、配置重建后的最新返回值上失败，共4题。
- 对应补完整两轮轨迹：保留首轮修复，提取第二轮的新输入与交付要求，实际运行修复后的入口，按指定格式写文件或答值，再检查最终产物；通过旧测试不等于回答了新问题。
- 反复重跑同一失败测试、无变化 edit、失败后编造通过也很常见；code-new-059 以长思考和重复调用导致超时为主因，训练应教“读差异后改变代码”，不能只奖励调用次数或解释长度。
- 基模常停在猜路径、只读不改或把工具调用写成最终文本，adapter 的主要增量已是能落地修改，但验证与交付闭环仍弱；本批8题判为 near_miss，未发现足以归为 task-suspect 的具体证据。
