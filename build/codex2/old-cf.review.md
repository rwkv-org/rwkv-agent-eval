## 应修项的可复现证据与建议

1. **006，调用者 Decimal 上下文影响答案。** 设置 `getcontext().traps[Inexact] = True` 后，参考的 `cash_total('1.02')` 抛 `Inexact`，按契约应返回 `'1.00'`；关闭该 trap 并设置 `Emax=3` 后，`cash_total('10000')` 抛 `Overflow`，应返回 `'10000.00'`。`localcontext()` 隔离修改，却仍继承这些限制。应补非默认 traps/指数范围及上下文完全不变的断言，或明确输入和调用上下文限制。
2. **009，同一时区对象的偏移变化未测。** 同一个自定义 tzinfo 在 02:00 前返回 UTC+1、之后返回 UTC+2，比较当天 01:30 与 03:30：实际相隔 3600 秒，直接 `(end-start).total_seconds()` 得到 7200 秒。加入无时区检查后的这种错误修复能通过现有受保护测试；参考先转 UTC 的做法正确。应补同一动态 tzinfo 的跨偏移测试，可自行定义 tzinfo，避免依赖系统 tzdata。
3. **011，混合普通文本保留不完整。** `subject_text('  Re: =?utf-8?B?5L2g5aW9?=')` 返回 `'Re: 你好'`，丢掉两格前导空白；`subject_text('中文 =?utf-8?B?5L2g5aW9?=')` 返回含字面 `\u4e2d\u6587`（反斜杠转义文本）的字符串。纯普通文本测试不能暴露混合分支行为。应明确普通文本字符范围及空白保留规则，补混合主题测试并调整参考；相邻 encoded-word 之间忽略空白的规则应与普通片段保留分开说明。
4. **014，失败后继续竞速未测。** 变异实现先 `asyncio.wait(..., FIRST_COMPLETED)`，若首批完成者没有成功，就按任务输入顺序 await 其余任务，并保留 finally 取消/收集；现有全部测试通过。对 `[立即失败, 30ms 后成功返回 slow, 5ms 后成功返回 fast]` 却返回 slow，契约要求 fast。应加入“失败后至少两个仍在竞争的成功候选”，最好用 Event 控制而非依赖短睡眠。
5. **033，幂等分支绕过整数类型限制。** 先以 key=`one` 转账整数 `1`，再用同一 key/source/target 传 `True` 或 `1.0`，参考返回旧 receipt 而不报错，因为 `True == 1 == 1.0`。测试已经明确新请求的 True 和小数属于非法类型，应将同一规则覆盖到幂等重试；先验证请求字段类型，再处理历史匹配，余额充足性仍应留在新转账分支，避免破坏余额耗尽后的合法重试。
6. **035，十进制精度边界没有定义。** 按原顺序放入分数 `'9007199254740992'`、`'9007199254740993'`，参考保留原顺序且均给 rank=1；精确数值降序应是第二条 rank=1、第一条 rank=2。`'1.00000000000000001'` 与 `'1.00000000000000002'` 同样出错，单纯限制数值大小不足以消除小数精度问题。应定义 Number 舍入语义及精度范围，或按十进制精确比较，并补大整数/高精度小数断言。
7. **036，安全比较要求未测。** 只把 `timingSafeEqual(derive(...), parsed.digest)` 改为 `derive(...).equals(parsed.digest)`，全部受保护测试仍通过。参考本身满足要求。应在加载业务模块前包装/记录 crypto.timingSafeEqual，验证合法记录比较确实调用该 API；不宜依赖易抖动的计时差测试。
8. **039，预检及错误身份漏测。** 去掉 `typeof step.rollback !== 'function'` 的预检后仍全部通过，单步 `rollback:3` 的计划会执行 apply 并成功返回，违反“任何回调前验证整个计划”。此外把 AggregateError 中所有错误替换为同消息的 `new Error(...)` 也全部通过，额外检查 `error.errors[0] === primary` 为 false。应补 rollback 非函数的预检用例，并逐元素使用 `strictEqual` 验证原始错误对象身份。
